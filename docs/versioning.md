# Independent action versions

Each directory under `actions/` is a private pnpm workspace package versioned by
Changesets. There is no global catalogue version or npm publication. The root
`package.json` manages tooling only.

| Reference | Purpose |
| --- | --- |
| `pr-comment-v1.2.3` | Immutable release of the `pr-comment` action |
| `pr-comment-v1` | Latest stable release of that action's major version 1 |
| Full commit SHA | Fixed repository revision; review nested action refs as well |
| `main` | Development; for testing only |

For example:

```yaml
- uses: grasdouble/Lufa-CICD/actions/setup-node-pnpm@setup-node-pnpm-v1
- uses: grasdouble/Lufa-CICD/actions/pr-comment@pr-comment-v2
```

Tags always reference repository commits, but each tag prefix belongs to one
action. Releasing `pr-comment` does not change `setup-node-pnpm`'s version or alias.

## Release metadata

- `pnpm-workspace.yaml` discovers the `actions/*` packages.
- `actions/<name>/package.json` holds the name `@grasdouble/cicd-<name>`, version
  and `private: true` flag. Keep directory and package names aligned.
- `.changeset/config.json` enables private-package versioning, disables CLI tags
  and keeps versions independent (`fixed` and `linked` are empty).
- `.changeset/*.md` describes the changes and explicit bump levels.
- `actions/<name>/CHANGELOG.md` is generated by Changesets during versioning.

New actions start at `0.0.0`, which the publisher skips. The initial major
changeset prepares the five actions for `1.0.0`. Let Changesets update versions
and changelogs through the version PR; avoid changing versions by hand.

## Choosing version bumps

Run from the repository root:

```sh
pnpm changeset
pnpm changeset status
```

Select each affected action and its bump level:

- **Patch**: compatible fix, dependency update, test or documentation change.
- **Minor**: backward-compatible feature or optional input.
- **Major**: incompatible change to an input, default, permission requirement or behavior.

For example, `.changeset/fix-comment-pagination.md` could contain:

```markdown
---
"@grasdouble/cicd-pr-comment": patch
---

fix: handle paginated pull request comments.
```

This bumps only `pr-comment`, regardless of the commit title. Every modified
action package needs a changeset, including action-specific docs and tests.
Combine related changes into one file; different packages can have different
bump levels within that file. Root-only tooling and documentation changes do not
need an action bump unless they change published behavior. Add changesets to
Dependabot PRs that modify action dependencies as well.

## Automated lifecycle

1. Merge action changes and their changesets into `main`.
2. Catalogue CI validates workflows and Changesets, runs tests, and smoke-tests
   the local setup action. The real CLI is tested in temporary workspaces.
3. The release job publishes any versioned actions already present on the
   validated main commit, then reconciles their major aliases. Unversioned
   `0.0.0` packages and already-published versions produce no new releases.
4. Changesets Action creates or updates `changeset-release/main`. The version PR
   consumes changeset files and updates each affected action's package version
   and changelog. Its version command is `pnpm run version:actions`.
5. Review and merge that PR after its checks pass.
6. The next successful main run publishes the new exact tags and GitHub Releases,
   then updates their major aliases.

Publication deliberately runs **before** Changesets prepares its version branch:
only versions on the validated main commit can be published. Changesets Action
uses version-only mode, without a publish command or automatic CLI tags/releases.
Its generic PR template may mention npm; catalogue publication remains GitHub-only.

Release jobs are serialized. A run that sees a newer `main` revision leaves
publication to that revision's CI run. PR runs never execute publication.

Ordinary PRs run `changeset status` against their remote base branch with full
Git history available. The Changesets version branch skips this presence check
because its changesets have already been consumed; all tests still run.

## GitHub setup

Enable Actions to create pull requests in **Settings → Actions → General**.
The release job requests `contents: write`, `pull-requests: write` and `packages: read`.
Both test and release jobs use the built-in `GITHUB_TOKEN` for package access.
In the GitHub Packages settings for `@grasdouble/lufa_config_agents`, grant
`grasdouble/Lufa-CICD` **Read** access under **Manage Actions access**: pnpm's
lockfile supply-chain checks fetch its metadata even during `--prod` installs.

For automatic CI on version PRs, use the existing `LUFA_CI_SECRET_WRITE` Actions
secret convention shared by the other Grasdouble repositories. Make this secret
available to Lufa-CICD, either as a repository secret or through an organization
secret's repository access settings. Its token must have access to this
repository's contents and pull requests. A GitHub App installation token can
also be used if token generation is added before the release steps.

Without this secret, the job uses `GITHUB_TOKEN`. That can manage PRs, tags and
releases when repository settings allow it, but its generated PR events do not
automatically trigger another Actions run. In that mode, run **Catalogue CI**
manually on the version PR branch and verify required checks before merging.

Configure tag rules to protect exact `<action>-vX.Y.Z` tags while allowing the
release identity to create and update `<action>-vX` aliases. If immutable GitHub
releases are enabled, attach releases to exact tags only, not to moving aliases.

## Publication and recovery

`scripts/publish-actions.mjs` uses the action package manifests from the validated
checkout. Before writing, it verifies package identity and the matching changelog
entry at the target commit. It creates `<action>-vX.Y.Z` tags and releases through
the GitHub API, without invoking npm or `changeset publish`.

Exact tags are never moved. If release creation fails after a tag was created, a
retry reuses that tag's original commit and release notes, even if main advanced.
An existing release with a deleted tag or inconsistent metadata requires repair
rather than silently recreating the tag at a different commit.

`scripts/sync-major-tags.mjs` reads all published releases and selects the highest
stable version for each configured action and major. It:

- ignores drafts, prereleases and unrelated tags;
- resolves exact tags to their actual commits, including annotated tags;
- verifies each release against that action's `package.json` version at the tagged commit;
- updates only major aliases, never exact version tags;
- preserves newer aliases and fails on conflicting versions or unexpected majors;
- reconciles existing releases on every successful release run, even when no new
  action version was published.

The publisher also passes its confirmed releases directly to alias reconciliation.
GitHub's releases listing can lag behind a newly created release; the direct
confirmation ensures its major alias is created in the same run. A later run
reconciles any missing alias from the complete releases listing.

If an API or permission error interrupts alias updates, fix the cause and rerun
**Catalogue CI** on `main`. Already-correct aliases are left in place. This also
repairs missing aliases without creating another release. The script's tests use
a mocked API and do not mutate repository tags.

## Internal action dependencies

`changesets-release` calls `setup-node-pnpm@setup-node-pnpm-v1`. Compatible setup
fixes are picked up through that alias. Adopting `setup-node-pnpm-v2` requires a
reviewed code change and a release of the consuming action, with a bump appropriate
to its own public contract. Changesets does not automatically update `uses`
dependencies between action directories; these are not npm workspace dependencies.

A full SHA pins an action's code, but not its dependencies that use mobile aliases.
Fully immutable execution requires pinning those internal refs as well.

## First publication and consumer migration

Merge the initial action files and `.changeset/initialize-action-versions.md`.
Review the version PR that bumps the five packages from `0.0.0` to `1.0.0`.
Publish those releases before merging consumer references to their major aliases.
Ensure `setup-node-pnpm-v1` exists before invoking `changesets-release`.

The catalogue's validation and publication use local actions and pinned third-party
tools, so they can bootstrap before the first catalogue tags exist. CI installs
only production tooling with the frozen pnpm lockfile; Changesets CLI is a root
dependency, while the private agent configuration package remains a local
development dependency.

The consumer release workflow now calls `actions/changesets-release` inside a
job's `steps`, with credentials under `with`. Consumers provide checkout, runner,
permissions, timeout and concurrency. Replace old global refs with per-action
aliases, for example `@v1` becomes `@pr-comment-v1` for `pr-comment`.

Before enabling production use, exercise setup and comment updates on a consumer
PR, and the release action in a disposable consumer repository with test packages.
Static validation does not establish remote registry or deployment permissions.

## Consumer updates

Major aliases receive compatible fixes on the next run. Exact tags and SHAs
require explicit updates. Consumers can enable Dependabot for action references:

```yaml
# .github/dependabot.yml in the consuming project
version: 2
updates:
  - package-ecosystem: github-actions
    directory: /
    schedule:
      interval: weekly
```
